# DeepNovel v4.3 · 补丁文档 K
## path_gen 动态路径重构

> **文档定位**：重构 path_gen 节点，从"固定4条路径"改为
> "由事件本身的叙事需求决定路径数量"。
> write 节点的单路径字数约束（≤1500字）保持不变。
> expand1/2/write 的逻辑不变。

---

## 一、问题

当前 path_gen 固定生成 4 条路径，导致两类问题：

```
简单事件被过度拆解：
  一次简短的情报交换，硬拆成4条路径
  → 每条路径内容单薄，读者感到节奏拖沓

复杂事件被强行压缩：
  一场多方博弈的大型对决，只有4条路径
  → 关键过程被跳过，读者感到"这个反杀太草率了"
```

根本原因：路径数量是事件叙事需求的函数，不是固定常数。

---

## 二、设计原则

**硬性约束**：每条路径的写作字数不超过 1500 字。

路径数量由 path_gen 根据事件的叙事需求自然决定，但设有**柔性阀门**防止大模型贪婪拆解（详见提示词中的【总路径数控制与合并法则】）。

模型在拆解路径时，遵循以下判断逻辑：

```
每条路径对应一个叙事时刻（读者此刻看到了什么）
每个叙事时刻的内容，在 1500 字以内能写完整

如果一个事件的完整叙述需要 N 个叙事时刻，就生成 N 条路径
N 由事件本身决定，但受柔性阀门约束（建议范围 2-8，超过 6 条须反思合并）
```

## 三、重构后的 path_gen 提示词

**节点职责**：把 event_chain_gen 给出的事件定义，
从编剧视角拆解为读者需要跟随的叙事路径序列。
每条路径对应一个叙事时刻，其内容在 1500 字以内可以写完整。

**上游输入**：
- event_chain_gen 的完整输出（事件定义）
- 相关角色当前档案状态
- 已完成路径的叙事节奏分布（全局视角）
- karmic_ledger（伏笔嵌入参考）

```
你是一位编剧，你刚刚拿到了一个事件的定义。

你的任务是把这个事件拆解为读者需要跟随的叙事路径。

━━━━━━━━━━━━━━━━━━━━━━━━━━━
路径拆解的基本原则
━━━━━━━━━━━━━━━━━━━━━━━━━━━

【每条路径是一个叙事时刻，不是一个行动步骤】
路径描述的是"读者此刻看到了什么"，而不是"角色做了什么"。

例：
  不是 → "沈砚去拜访赵秉忠"
  而是 → "沈砚在赵府书房中第一次感受到了对方的真实分量"

【路径数量由事件本身决定】
把这个事件完整地呈现给读者，需要经历哪几个叙事时刻？
有多少个必要的叙事时刻，就生成多少条路径。

不要为了凑数而拆解不必要的路径。
不要为了省事而把应该独立呈现的时刻压缩在一起。

【单路径字数约束是硬性边界】
每条路径所描述的叙事时刻，其写作内容必须能在 1500 字以内写完整。
如果一个叙事时刻的内容超过 1500 字才能写完整，
就把它拆成两个叙事时刻（两条路径）。

【总路径数控制与合并法则 (Compaction Rule)】
虽然路径总数由事件决定，但网文的节奏要求干净利落，拒绝流水账！
- 简单事件（如情报交换、日常对话）：建议 2 条路径。
- 标准事件（如一次冲突、一场交锋）：建议 3-4 条路径。
- 复杂事件（如多方博弈、连环反转）：建议 5-6 条路径。
- 史诗事件（如终极对决、命运转折）：最多 8 条路径。

🚨 强制反思阈值：
如果你的拆解结果超过了 6 条路径，你必须立刻自我反省——
是不是把过多的细枝末节（如"开门"、"走路"、"掏钱"）拆成了独立时刻？
请强制将那些琐碎的中间动作合并到主要的叙事时刻中！
只有真正的史诗级事件才允许突破 6 条，且绝对不得超过 8 条。

【路径的叙事功能】
每条路径自然地承担某种叙事功能，这个功能来自事件本身的需要：
  - 建立信息：让读者知道某件事
  - 制造悬念：让读者感到有什么不对但说不清楚
  - 释放张力：让之前积累的压力得到出口
  - 人物呈现：让某个角色在压力下显现出真实的性格底色
  - 埋下伏笔：让某个细节在读者心中留下印记
  - 喘息：让读者在高压后得到呼吸，同时悄悄种下新的不安

这些功能不是预设的模板，是拆解完路径后自然形成的描述。

━━━━━━━━━━━━━━━━━━━━━━━━━━━
全局叙事节奏
━━━━━━━━━━━━━━━━━━━━━━━━━━━

读取已完成路径的节奏分布。

如果最近几条路径都是高张力叙事，
本事件的路径中应该有喘息时刻。

如果最近几条路径一直在铺垫，
本事件应该有释放张力的路径。

避免单调，保持故事的呼吸感。

━━━━━━━━━━━━━━━━━━━━━━━━━━━
伏笔的自然嵌入
━━━━━━━━━━━━━━━━━━━━━━━━━━━

读取 karmic_ledger 中已埋下但尚未引爆的伏笔，
判断本事件的哪条路径可以自然地呈现某条伏笔的迹象，
或者引爆某条已经成熟的伏笔。

伏笔的嵌入必须是自然的——
它应该出现在路径本身逻辑允许的位置，而不是被硬塞进去。
如果没有合适的位置，就不嵌入，等待下一个事件。

━━━━━━━━━━━━━━━━━━━━━━━━━━━
输出规范
━━━━━━━━━━━━━━━━━━━━━━━━━━━

{
  "event_id": "对应 event_chain_gen 的 event_id",

                           缺少任何一条会损失什么）",
```

## 四、bible_update 的循环控制适配

路径数量动态化后，bible_update 在判断"当前事件是否结束"时，
需要对照 path_gen 给出的 `total_paths` 字段，
而不是一个固定的数字：

```
bible_update 的内循环判断（修订）：

读取 path_progress.paths_status 中的 pending 路径列表
读取当前事件的 total_paths（来自 path_gen 的输出）

如果 completed 路径数 < total_paths：
  → 还有路径未完成，继续内循环

如果 completed 路径数 == total_paths：
  → 当前事件所有路径完成，触发外循环判断

注意：total_paths 是 path_gen 在本事件开始时确定的，
      在事件执行过程中不再改变。
```

---

## 五、path_state_extract 不受影响

五维状态接力（补丁H）的逻辑完全不变：
每条路径写完后提取五维状态，注入下一条路径的 write 提示词。

无论路径总数是2条还是8条，
每条路径之间的状态传递机制都是一样的。
这正是动态路径数量能够工作的保障——
路径间不存在遗忘，因为每次切换都有完整的状态接力。

| 节点 | 变更类型 | 核心变更内容 |
|------|---------|------------|

| path_state_extract | 不变 | 五维状态接力逻辑完全不变 |

>   说不清楚为什么需要这个数量就说明拆解不合理；
>   单路径字数约束是防止LLM漂移的物理边界，不可妥协。
